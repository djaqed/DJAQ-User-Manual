Purpose of This Manual

#

This document exists because human beings are very fond of undocumented APIs.

Djaq is generally happiest when expectations, intentions, boundaries, and system states are visible. Many misunderstandings happen not because anybody is malicious or uncaring, but because one person expects another person to infer information that was never explicitly transmitted.

This manual is an attempt to make the interface visible.

It is not:

  • a demand that everybody interact with Djaq in exactly one way;
  • an excuse for harmful behavior;
  • a replacement for conversation;
  • a declaration that other people's boundaries matter less;
  • a claim that every behavior is immutable;
  • a psychiatric report.

It is:

  • a compatibility document;
  • a troubleshooting guide;
  • a map of common failure modes;
  • a list of hard boundaries;
  • a record of patterns that repeatedly make communication easier;
  • a way to reduce unnecessary guessing.
Golden rule

If the documentation and the person in front of you disagree, believe the live system. Ask.

System Overview

#

Djaq is a highly analytical, pattern-oriented, curiosity-driven system optimized for:

  • understanding complex systems;
  • identifying patterns, edge cases, and inconsistencies;
  • acquiring alarming amounts of information about interesting subjects;
  • learning mechanisms rather than memorizing isolated rules;
  • solving difficult problems once engagement has initialized;
  • direct, detailed communication;
  • building tools, rules, checklists, scripts, routines, and external systems when automatic functions are unreliable;
  • maintaining deep attachment to people, ideas, projects, stories, and interests;
  • iterative experimentation: TRY -> OBSERVE -> UPDATE MODEL -> TRY AGAIN;
  • turning ambiguity into a model that can be reasoned about.

A useful mental model is not “computer instead of person.” Djaq is obviously a person. The computer metaphor is useful because it separates concepts people otherwise mash together:

  • installed capability;
  • currently available resources;
  • task priority;
  • process state;
  • input quality;
  • context switching;
  • thermal load;
  • background processes;
  • failure recovery.

Several functions that appear automatic on other human hardware require conscious computation here. Successful execution does not imply low processing cost.

Core Architecture

#

Djaq generally performs best under the sequence:

PURPOSE -> STRUCTURE -> RELEVANCE -> ENGAGEMENT -> MOMENTUM -> DEPTH

When the chain completes, the result may be intense concentration, rapid learning, unusually deep troubleshooting, or a multi-hour rabbit hole that started with “huh, I wonder why.”

The common failure point is before ENGAGEMENT.

TASK EXISTS
   |
   v
IS IT RELEVANT NOW? -- no --> background archive / oblivion
   |
  yes
   v
IS NEXT ACTION CLEAR? -- no --> activation stall
   |
  yes
   v
ENOUGH INTEREST / URGENCY / MOMENTUM? -- no --> scheduler starvation
   |
  yes
   v
EXECUTE

2.1 Capability and access are separate

A hard task can be easy to execute if it is interesting, urgent, concrete, and already in motion.

An easy task can be nearly impossible to initiate if it is vague, distant, boring, contextless, or requires several invisible setup steps.

Therefore:

Difficulty starting does not reliably predict difficulty doing.

A three-hour technical problem may be easier than sending a two-line email.

Opening the file may be harder than fixing the file.

This is expected system behavior.

Resource Model

#

CPU — conscious processing

Used heavily for:

  • decoding ambiguous social information;
  • switching contexts;
  • suppressing distracting inputs;
  • figuring out emotions in real time;
  • planning an unfamiliar task;
  • pretending an arbitrary rule makes sense when it does not;
  • translating vague requests into executable actions.

RAM — working memory

Fast, useful, and not reliably persistent.

Items held only in RAM can disappear when:

  • another process interrupts;
  • a new interesting idea starts;
  • sensory load increases;
  • context changes;
  • time passes;
  • the item is important but not immediately actionable.

Recommendation: write things down.

Storage — long-term memory

Can be excellent, especially for:

  • systems;
  • patterns;
  • stories;
  • conceptual relationships;
  • special interests;
  • oddly specific facts;
  • things attached to context.

This can create the apparently absurd state:

Remembers a niche fact from eleven years ago; forgets why he opened the refrigerator.

No contradiction exists. Different subsystem.

GPU — visualization / pattern engine

Performs well when information can be represented as:

  • diagrams;
  • layouts;
  • examples;
  • screenshots;
  • side-by-side comparisons;
  • visible structure;
  • “show me what it should look like.”

Network — social bandwidth

Can be excellent. Can also saturate.

Good network performance does not mean infinite bandwidth.

Cooling — recovery

Required after prolonged:

  • social emulation;
  • sensory exposure;
  • conflict;
  • high-context work;
  • performance;
  • multitasking;
  • sustained self-monitoring.

Boot Sequence

#

For unfamiliar tasks, the ideal boot sequence is:

  1. What are we trying to accomplish?
  2. Why does it matter?
  3. What constraints are real?
  4. What does “done” look like?
  5. What is the next executable action?

Skipping directly to step 5 without enough context can generate resistance because the system is trying to infer the missing architecture.

Providing twenty minutes of context when only one sentence matters can generate the opposite problem.

Best input is sufficient context, low noise.

The WHY? Command

#

When Djaq asks “why?”, the default interpretation should be:

REQUEST: return underlying rule / mechanism / constraint

It is frequently not:

REFUSAL
CHALLENGE_TO_AUTHORITY
ARGUMENT_FOR_SPORT

Djaq learns systems by understanding how parts relate. Once the reason exists, the instruction can become part of a reusable model instead of a disconnected fact.

Good response

“Because this field is what the downstream process keys on. If it changes, the lookup fails.”

Also good

“There is no elegant reason. The vendor requires it, so that requirement is the constraint.”

The latter is surprisingly satisfying. An arbitrary rule with a known source is still a modelable rule.

Pattern Acquisition Engine

#

Djaq learns particularly well by:

EXAMPLE -> RULE -> COUNTEREXAMPLE -> EDGE CASE -> GENERAL MODEL

Common behaviors include:

  • asking the functional difference between two similar options;
  • testing whether a proposed rule still works in a weird case;
  • deliberately proposing an alternate approach to see where it breaks;
  • using screenshots or live examples to compare expected vs. actual output;
  • correcting the model quickly when new evidence appears;
  • wanting to know not merely what works, but why this works and that does not.

If an explanation seems to be producing many follow-up “what about…” questions, this usually means the model is still being built—not that the original answer was ignored.

Attention Scheduler

#

Djaq does not possess one stable quantity called “attention.” Attention behaves more like a priority scheduler whose weights include:

interest
novelty
urgency
immediate relevance
complexity
challenge
sensory environment
existing momentum
social accountability
visible progress

Consequently:

STATE A: research one subject for five hours
STATE B: reread one paragraph four times

Both are normal.

7.1 Hyperfocus

Hyperfocus is useful, enjoyable, and potentially resource-hungry.

During strong engagement:

  • time may become less visible;
  • hunger/thirst/fatigue signals may be deprioritized;
  • unrelated obligations may stop existing perceptually;
  • interruptions can feel unusually expensive;
  • stopping may be harder than continuing.

Helpful intervention

Transmit the competing context explicitly:

“You don't need to stop this forever. You have to leave in 20 minutes, so this is the save-point warning.”

This is better than:

“You've been doing that too long.”

The first restores missing scheduler information. The second provides judgment without actionable state.

Activation Engine

#

A task can be conceptually easy and still fail to launch.

Common activation blockers:

  • no obvious first step;
  • deadline too distant;
  • task feels administratively meaningless;
  • too many possible starting points;
  • high setup cost;
  • expected interruption;
  • insufficient stimulation;
  • task is emotionally loaded;
  • prior failed attempt left negative cache entries;
  • “I should do this” exists without a current trigger.

8.1 Effective activation techniques

  • reduce to the first physical action;
  • put needed tools in sight;
  • body-double;
  • start while discussing it;
  • create a short sprint;
  • use an external deadline;
  • attach the task to something already happening;
  • define a visible stopping point;
  • make it a puzzle;
  • create a checklist;
  • ask for a screenshot/progress state;
  • turn the task into a system rather than a vague obligation.

8.2 Ineffective activation techniques

  • shame;
  • “just do it”;
  • repeating that it is easy;
  • listing all consequences while providing no first step;
  • assuming more importance automatically creates more activation;
  • removing useful supports to prove they should not be necessary.

External Executive Function

#

Djaq deliberately uses external systems to compensate for unreliable internal timing and memory.

Supported peripherals include:

  • calendars;
  • alarms;
  • reminders;
  • notes;
  • spreadsheets;
  • scripts;
  • checklists;
  • automation;
  • scheduled routines;
  • people;
  • AI tools;
  • physical staging of objects;
  • screenshots;
  • naming systems;
  • “tell me what the next step is” conversations.

This is not cheating.

This is system design.

Design principle

If a function is unreliable internally but reliable when externalized, externalize it.

Djaq often uses conversational tools as external RAM, debugger, scheduler, comparator, and rubber duck while retaining final judgment and system understanding.

Time Interface

#

This is an excellent example of system adaptation: if raw time estimation is unreliable, use a stable external reference.

Directness and Tone

#

Djaq generally experiences clear information as safer than ambiguous politeness.

However, directness is not the same as indifference to tone. In practice, Djaq often spends considerable effort choosing wording that is:

  • exact;
  • fair;
  • unlikely to create unnecessary conflict;
  • difficult to misinterpret;
  • proportionate to the actual issue.

This creates an interesting combination:

PREFERS DIRECT COMMUNICATION
+
CARES ABOUT PRECISE SOCIAL IMPACT

When wording matters, iterative drafting is normal:

“That's accurate, but it doesn't sound like what I mean.”

The goal is not merely semantic correctness. It is transmission fidelity.

Interrupt Handling

#

Interruptions have variable cost.

An interruption is especially expensive when:

  • the active task has many state variables;
  • a solution is nearly assembled;
  • the system has just achieved momentum;
  • returning requires reconstructing context;
  • multiple windows/tools are involved;
  • the interruption is unrelated and vague.

Better interruption

“When you hit a stopping point, I need five minutes about dinner.”

Worse interruption

“Hey—quick question…”

There are no quick questions. There are only undocumented context switches.

Social Processing

Djaq likes people.

  • a defined purpose;

SOCIAL CAPABILITY != SOCIAL EFFORTLESSNESS

Djaq may appear relaxed while performing substantial background processing.

“You seemed fine” is therefore not a reliable diagnostic command.

Shutdown / Low-Output State

#

When load exceeds available resources, output may decrease rather than become dramatic.

Possible signs:

  • shorter answers;
  • silence;
  • delayed responses;
  • reduced facial expression;
  • difficulty choosing;
  • desire to leave;
  • less tolerance for additional questions;
  • apparent emotional flatness;
  • “I don't know” loops.

Do not immediately assume anger, punishment, or withdrawal of affection.

Recommended sequence:

REDUCE INPUT -> RESTORE SAFETY/CLARITY -> WAIT -> DEBUG LATER

Trying to force high-bandwidth emotional conversation during low-output state may worsen the fault.

18.1 Triggered shutdown is a safety event, not a debate

Some inputs can activate an older threat model before the present situation has been consciously classified. The visible response may be escape, freezing, silence, crying, reduced language, or complete shutdown.

The first task is not to prove that the current situation is safe. The first task is to restore enough present-state safety for the system to evaluate it.

Recommended sequence:

STOP ESCALATION -> REDUCE INPUT -> ORIENT TO PRESENT -> OFFER SIMPLE CHOICES -> WAIT -> DEBRIEF LATER

Useful questions:

  • “Do you want to leave, move somewhere quieter, have company, or have space?”
  • “Would practical help be useful, or should I just stay nearby?”
  • “Do you want to talk now, later, or not at all?”

Do not require an explanation, emotional label, or trauma history while the response is active. Do not use elapsed time as evidence that the reaction should no longer exist.

18.2 Grief validation protocol

Another person's pain does not invalidate Djaq's pain, and Djaq's pain does not claim exclusive ownership of the event.

Useful response:

“I know this affects other people too. I am listening to what it is like for you.”

Less useful response:

“Everyone is going through it.”

The second statement may be factually true while still answering a claim Djaq did not make. Validate the local experience before widening the frame.

18.3 High-stakes transition protocol

Major moves, housing changes, relationship transitions, job changes, and other losses of a stable environment may carry more load than their logistics explain. Treat them as changes to safety, identity, routine, and control—not merely a checklist of tasks.

For a significant transition:

1. Give the earliest reliable notice.
2. Explain what is changing, why, and what is still unknown.
3. Identify what will remain stable.
4. Divide the work into visible, owned steps.
5. Do not leave Djaq carrying the whole transition alone.
6. Protect sentimental, sensory, and continuity anchors.
7. Schedule recovery time and a post-transition check-in.

Unexpected changes may still be unavoidable. Unexplained changes are more destabilizing than clearly communicated ones.

18.4 Help and trust protocol

Djaq may need help while also needing clear boundaries around the helper's role. Assistance does not purchase authority, access, secrecy, loyalty, or exemption from scrutiny.

Good help has an explicit contract:

WHAT HELP IS OFFERED
WHAT THE HELPER NEEDS OR EXPECTS
WHAT DECISIONS REMAIN DJAQ'S
WHEN THE ARRANGEMENT ENDS OR GETS REVIEWED

Hidden motives or changing terms can damage trust far beyond the immediate event. Transparent help is easier to accept and safer to rely on.

Sensory I/O

#

Djaq actively curates sensory input.

Common controls may include:

  • headphones;
  • chosen background sound;
  • lighting changes;
  • temperature management;
  • avoiding wet/cold sensations;
  • avoiding specific food textures;
  • changing location;
  • choosing predictable sensory environments.

These are preventative resource-management techniques.

If Djaq says a sound, texture, temperature, or environment is bothering him, that statement is generally sufficient input. Visible distress is not required for validity.

Design principle

PREVENT OVERLOAD > RECOVER FROM OVERLOAD

Learning Interface

#

Djaq tends to learn best when allowed to interact with the concept.

Strong modes:

  • explain the mechanism;
  • show a real example;
  • compare two similar things;
  • let Djaq predict the output;
  • identify why the prediction failed;
  • repeat with an edge case;
  • build a compact rule;
  • apply immediately.

Less effective mode:

MEMORIZE THIS BECAUSE THE COURSE SAYS SO

Excellent teaching prompt

“What do you think will happen here, and why?”

Excellent correction

“Your model is right except for this one assumption.”

This preserves the system while patching the bug.

Troubleshooting Style

#

Djaq is an iterative troubleshooter.

Typical loop:

1. Observe output
2. Form hypothesis
3. Change one variable
4. Retest
5. Compare state
6. Update hypothesis
7. Escalate only after evidence

Visual state is highly useful. Screenshots, photos, logs, exact errors, and “this is what it looks like right now” often outperform generalized descriptions.

If advice produces an unexpected result, Djaq is likely to return with evidence rather than simply accept that the instructions “should” have worked.

This is not stubbornness. The observed system state outranks the documentation.

Decision Engine

#

Djaq often decides by building a functional model rather than choosing from vibe alone.

Common questions:

  • What is the practical difference?
  • What does each option optimize for?
  • What changes if I choose A?
  • Is there another option that fits the actual use case better?
  • What if I combine them?
  • Why not do the obvious alternative?
  • What constraint am I missing?

A recommendation without reasoning may be accepted provisionally but is less reusable.

A recommendation with clear tradeoffs becomes part of the internal library.

Autopilot Mode

#

Djaq enjoys some activities specifically because they can become dense, rhythmic, repeatable, and low-decision once the pattern is established.

The useful progression is:

UNDERSTAND PATTERN -> VERIFY PATTERN -> MUSCLE MEMORY -> AUTOPILOT

Do not confuse a desire for autopilot with a dislike of complexity. Frequently the enjoyable part is mastering the structure deeply enough that complexity becomes rhythm.

This applies to crafts, music, repetitive physical tasks, and some workflows.

Novelty vs. Routine Conflict

#

Two legitimate system demands coexist:

SUBSYSTEM A: PREDICTABILITY PLEASE
SUBSYSTEM B: NEW THING NOW

Possible output:

  • loves established routines but gets bored with stale processes;
  • wants a plan but modifies it while executing;
  • wants predictable obligations but interesting content;
  • benefits from repeated structure with variable challenges;
  • may build elaborate systems and then require novelty to keep using them.

Best design pattern:

stable frame, variable content

Examples:

  • fixed learning time, changing material;
  • familiar workflow, new problem;
  • recurring social setting, different conversations;
  • known craft structure, changing pattern/colors;
  • clear game build, experimentation inside it.

Physical Interface & Bodily Autonomy

#
HARD SAFETY RULE

Bodily autonomy is sacrosanct.

Djaq will not intentionally touch another person in a way they have not invited through words or clearly communicated action.

The reciprocal expectation is the same.

Each person retains authority over their own:

  • physical contact;
  • appearance;
  • clothing;
  • sexuality;
  • medical decisions;
  • physical boundaries.

Advice may be offered.

Authority remains with the person whose body is involved.

Attraction / Limerence / New-Person Excitement

#

Djaq may experience unusually intense interest in a new person before the system has classified the attachment.

NEW PERSON IS FASCINATING

Relationship Architecture

#

Relationships are primarily modeled as individual connections:

DJAQ <-> PERSON A
DJAQ <-> PERSON B

They are not automatically merged into:

PERSON A's relationship with PERSON B
        controls
DJAQ's relationship with PERSON B

People are welcome to provide:

  • safety information;
  • relevant context;
  • concerns;
  • perspectives;
  • warnings;
  • evidence of behavior Djaq may not have seen.

Djaq retains responsibility for deciding what those facts mean for his own relationship.

Relationships are not governed by committee.

This does not require neutrality toward wrongdoing. It means decisions are made from Djaq's values and evidence, not outsourced social pressure.

Partner Interface

#

Romantic relationships can carry unusually high emotional significance, so ambiguity about relationship state may consume more processing than a clearly defined disagreement.

Very useful message:

“I'm frustrated about X. We are okay. I need to talk about X, not reevaluate us.”

This transmits two independent states:

ISSUE_STATUS = ACTIVE
RELATIONSHIP_STATUS = SECURE

Without explicit status data, the system may waste resources determining whether one implies the other.

Clarity is not less intimate than intuition.

For Djaq, clarity is often a form of intimacy.

Conflict Protocol

#

Healthy conflict is supported.

Preferred sequence:

1. Identify specific issue
2. State impact
3. Clarify relationship state if relevant
4. State desired change
5. Let Djaq ask mechanism/clarification questions
6. Agree on next behavior
7. Revisit if implementation fails

Less compatible methods:

  • silent tests;
  • vague punishment;
  • strategic withdrawal intended to provoke pursuit;
  • “nothing's wrong” when something is wrong;
  • recruiting a social jury before talking directly;
  • expecting intent to be inferred from emotional intensity.

Questions during conflict do not necessarily mean refusal to accept impact. Djaq often needs a coherent causal model before a behavior change becomes durable.

Anti-Manipulation Security Policy

#

Supported:

  • persuasion;
  • disagreement;
  • requests;
  • negotiation;
  • emotional honesty;
  • “I really want this”;
  • consequences stated truthfully;
  • changing one's mind.

Considered hostile input:

  • deliberate deception;
  • guilt intentionally used as leverage;
  • knowingly false or misleading information;
  • manufactured social pressure;
  • weaponized vulnerability;
  • attempts to exploit empathy;
  • deliberate ambiguity intended to control behavior;
  • making Djaq prove care by passing hidden tests.

This policy is reciprocal.

Djaq tends to perform strongly when work contains:

  • a real system to understand;
  • a concrete failure to diagnose;
  • visible inputs/outputs;
  • permission to inspect underlying mechanics;
  • meaningful autonomy;
  • clear constraints;
  • a problem nobody has fully modeled yet.

Less friendly conditions:

  • arbitrary process with no visible purpose;
  • repetitive administrative work with delayed relevance;
  • vague responsibility boundaries;
  • unclear ownership;
  • unnecessary meetings with no decisions;
  • instructions whose important constraints are buried in noise.

35.1 Best collaboration pattern

Provide:

GOAL
KNOWN STATE
CONSTRAINTS
WHAT HAS ALREADY BEEN TRIED
DEFINITION OF DONE

Then allow room for investigation.

35.2 Status requests

Concrete requests work better than “where are we on this?”

Better:

“What is working, what is blocked, and what do you need from me?”

This produces useful state data instead of forcing a full project reconstruction on demand.

35.3 Human outcome check

Djaq evaluates systems by whether they accomplish their real purpose for the people inside them, not only whether a formal target was technically met.

Before committing to a major goal, ask:

WHAT DOES SUCCESS PRODUCE?
WHO BENEFITS?
WHO PAYS THE COST?
WHAT MUST NOT BE SACRIFICED?
HOW WILL WE KNOW THE SYSTEM WORKS IN PRACTICE?

A milestone can be achieved while the larger system fails. “Technically complete” is not the same as “successful.”

Frequently Asked Questions

#

“Are you arguing with me?”

Possibly. But if the response contains many mechanism questions, first consider whether Djaq is debugging the premise rather than rejecting the goal.

“Why can you remember that and not this?”

Because memory systems are not sorted by objective importance. Context, interest, salience, and external cues matter.

“Why do you need me to say something that seems obvious?”

Because explicit packets have checksums. Hints do not.

“Do reminders annoy you?”

Usually much less than people fear. A useful reminder is often a retransmission, not a criticism.

“Why did you ask me the same kind of question five different ways?”

The model probably has an unresolved edge case.

“Why are you suddenly extremely invested in this random subject?”

Scheduler found a shiny dependency. Estimated duration unavailable.

“Why do you want structure and then immediately change the structure?”

The structure is a scaffold, not a religion. New data can justify a patch.

“Why are you quiet?”

Unknown. Possible low battery, overload, deep thought, emotional classification, hyperfocus, or simply nothing to say. Query directly rather than inferring.

“How do I know if you're flirting?”

This is exactly why the manual recommends words.

“How do I tell you you've crossed a line?”

Plainly, specifically, and as soon as practical. Useful bug reports are welcome.

“What if my needs conflict with yours?”

Then we have a compatibility problem to negotiate, not a villain to identify.
